\chapter{Detailed Requirement Derivation Matrices}
\label{app:requirement_derivation}

This appendix provides the complete, requirement-by-requirement documentation underlying the derivation methodology described in Section \ref{sec:security_requirements}. It contains the 14 security requirements derived from Annex III, Sections 1.1.9 and 1.2.1 of \hyperref[subsec:eu_machinery_regulation]{\textbf{Regulation (EU) 2023/1230}}, together with their detailed mapping to \hyperref[subsec:pren_50742]{\textbf{prEN 50742}} and, subsequently, to \hyperref[subsec:iec_62443]{\textbf{IEC 62443-4-2}} Component Requirements (CRs), Requirement Enhancements (REs), and component-type-specific instantiations such as Embedded Device Requirements (EDRs). The three tables correspond to the three derivation stages and share a common requirement identifier (RQ-XXX) to preserve traceability across all stages.

\chapter{Secure Development Lifecycle}
\label{app:SecureDevelopmentLifecycle}

This appendix provides a high-level overview of the Secure Development Lifecycle underlying the verification framework developed in Chapter \ref{chap:methodology}. The diagram condenses a more detailed internal reference model, \emph{Secure System Development Lifecycle.drawio}, which decomposes each depicted activity into further sub-steps; only the top-level activity flow and its governing feedback relationships are reproduced here, consistent with the appendix's role as a supporting artifact rather than a full lifecycle discussion.

The overview illustrates that cybersecurity is not confined to a single validation step prior to release, but is integrated as a continuous concern across the entire product lifecycle. Following an initial definition of scope, stakeholders, and security objectives, a combined requirements-engineering and risk-assessment activity establishes the applicable Security Level based on a Threat Analysis and Risk Assessment (Section \ref{subsec:tara}). Its results inform secure design, expressed through a dedicated security architecture and a corresponding set of detailed countermeasures, which in turn constrain secure implementation during development. Verification and validation are carried out through static and dynamic analysis, dedicated test strategy and preparation, and security test execution, whose outcomes feed the release decision. Once released, the product enters operation and maintenance, where continuous monitoring supports ongoing vulnerability management. Documentation and traceability are maintained as a cross-cutting thread throughout all activities, so that every decision remains attributable to its originating risk assessment or verification result.

The dashed connections in the diagram represent the feedback loops that distinguish this lifecycle from a strictly sequential process: findings from security test execution are returned to secure implementation for remediation, architectural constraints identified during design are fed back into the risk assessment, and observations from continuous monitoring trigger a reassessment or incident response that re-enters the lifecycle at the risk-assessment stage. These loops embody the principle of continuous improvement and correspond to the process-oriented practices of IEC 62443-4-1 (Section \ref{subsec:iec_62443}) as well as the DevSecOps feedback mechanism discussed in Section \ref{subsec:verification_lifecycle_governance}, in which findings observed at runtime are fed back into planning rather than treated as terminal outcomes.
