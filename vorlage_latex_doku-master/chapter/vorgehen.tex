\section{Regulatory Analysis under the EU Machinery Regulation}
\label{sec:regulatory_analysis}

%To bridge the gap between abstract legal mandates and practical security testing for industrial gateways, a rigorous analysis of \hyperref[subsec:eu_machinery_regulation]{Regulation (EU) 2023/1230} is required. The primary objective is to extract and formalize all mandatory cybersecurity requirements that apply to components operating at the physical and logical IT/OT boundary. While the Machinery Regulation addresses product safety holistically, cybersecurity requirements are predominantly anchored in Annex III, Sections 1.1.9 (\textit{Protection against corruption}) and 1.2.1 (\textit{Safety and reliability of control systems}). For an industrial gateway, which routes, translates, and filters data between untrusted IT networks and safety-critical OT domains, these provisions impose explicit technical duties on the manufacturer.
%
%Under Annex III, Section 1.1.9, the regulation establishes four core mandates to prevent digital manipulation from impairing safety functions. First, the connection of any external device must not create a hazardous situation under any operational state. Second, hardware components transmitting safety-relevant data or control signals must be resilient against accidental or deliberate corruption. Third, software applications, firmware, and configuration datasets essential for compliance with safety requirements must be identified and protected against unauthorized alteration or corruption using mechanisms. Fourth, the system must actively collect and retain immutable evidence regarding legitimate and illegitimate interventions, configuration changes, or access attempts to ensure complete auditability.
%
%Complementarily, Section 1.2.1 explicitly addresses the operational behavior of control systems under malicious conditions. Because industrial gateways frequently act as front-line communication proxies for underlying Programmable Logic Controllers (PLCs), the control systems and their associated gateway interfaces must be engineered to withstand reasonably foreseeable malicious attempts by third parties without inducing a hazardous state. Furthermore, any loss, corruption, or disruption of network data transmission must be handled gracefully, ensuring that communication failures default to a predefined safe state.
%
%Beyond functional implementation, Regulation (EU) 2023/1230 fundamentally alters the requirements for conformity assessment and technical documentation under Article 10(2) and Annex IV, Part A. Manufacturers can no longer rely solely on passive self-declarations regarding software integrity. To demonstrate compliance during the conformity assessment process, manufacturers must provide concrete, empirical evidence within the technical documentation. This documentation must encompass a formal cybersecurity threat and risk assessment covering the entire lifecycle, detailed technical specifications of all implemented protective measures, and empirical test reports proving that the implemented security controls effectively mitigate identified threats under realistic operational conditions.

\section{Normative Mapping and Technical Security Requirements}

Because an industrial gateway is an IACS component operating at the IT/OT boundary, compliance is verified against the Component Requirements (CRs) of IEC 62443-4-2, supported by testing methodologies from NIST SP 800-115 and OWASP WSTG, and aligned with the lifecycle verification practices of IEC 62443-4-1 (SVV-3).

\section{System Analysis} 
\label{sec:system_analysis}
The purpose of the system analysis is to establish a detailed understanding of the System Under Consideration (SUC). This includes the system architecture, available interfaces, communication mechanisms, critical assets, trust boundaries, and the overall attack surface. 

\subsection{System Overview} 
\label{subsec:system_overview}

 The Safe Remote I/O (SRIO) is a fieldbus-based safety device used within industrial automation systems. It acquires binary 24 V input signals from safety sensors and transmits them to a higher-level safety controller (F-Host) via PROFIsafe communication. In addition, the device receives output commands from the F-Host and controls connected actuators through safety-related digital outputs. The device supports both safety-related and non-safety-related communication functions. The system consists of the following main components: 
 \begin{itemize} 
 	\item \textbf{Communication Module (COM):} Provides Ethernet-based communication, PROFINET connectivity, IoTCore functionality, web services, firmware update handling, and data storage access
 	\item \textbf{System Communication (SysCom):} Internal SPI-based communication channel between COM and SCPU
 	\item \textbf{Safety CPU Module (SCPU):} Implements the safety functions using a 1oo2 architecture consisting of two independent safety controllers, cross-communication mechanisms, and a watchdog
 	\item \textbf{Power Supply Module (PS):} Supplies all internal system components.
 	\item \textbf{Digital Input Module (DI):} Provides six safe digital input channels.
 	\item \textbf{Digital Output Module (DO):} Provides two safe digital output channels.
 \end{itemize} 
 
 \subsection{System Architecture} 
 The SRIO architecture separates safety-related and non-safety-related functionality. The COM module acts as the communication gateway. It handles PROFINET communication, the IoTCore web interface, firmware update services, and network management functions. The COM module is based on a dedicated communication processor and a fieldbus controller. The SCPU module implements the safety application. Two independent safety controllers execute the safety logic and exchange diagnostic information through internal communication channels. A watchdog mechanism supervises correct system operation. Communication between COM and SCPU is performed via the SysCom interface. Safety-relevant communication is transmitted using the black-channel principle, where PROFIsafe messages are transported over standard PROFINET communication. 
 
 \subsection{Interfaces and Communication Channels} 
 The SRIO exposes several external and internal interfaces. 
 
 \subsubsection{External Interfaces} 
 
 \begin{itemize} 
 	\item Ethernet interface for PROFINET and IoTCore communication
 	\item Power supply connectors including daisy-chain functionality
 	\item Rotary switches for addressing and special operating modes
 	\item Safe digital input interfaces (F-DI)
 	\item Safe digital output interfaces (F-DO)
 	\item LED indicators for device status visualization
 \end{itemize} 
 
 \subsubsection{Internal Interfaces} 
 
 \begin{itemize} 
 	\item SysCom interface between COM and SCPU
 	\item IPC interface between SCPU1 and SCPU2
 	\item JTAG debugging interfaces for development and maintenance purposes
 \end{itemize} 
 
 
 \subsection{Communication Protocols} 
 The following communication protocols are supported by the system: 
 \begin{itemize} 
 	\item \textbf{PROFINET:} Industrial Ethernet protocol used for process communication between the SRIO and the F-Host
 	\item \textbf{PROFIsafe:} Safety communication protocol operating on top of PROFINET according to the black-channel principle
 	\item \textbf{HTTP/JSON:} Used by the IoTCore for diagnostics, monitoring, device information, and firmware update handling 
 \end{itemize} 
 The system supports HTTP communication only. HTTPS, MQTT, and WebSocket communication are not implemented. 
 
 \subsection{System Classification} 
 The SRIO is classified as a safety-related industrial automation component. 
 \begin{itemize} 
 	\item IEC 61508 SIL 3 
 	\item EN ISO 13849-1 Performance Level e (PL e), Category 4 
 \end{itemize} The device serves as a safety gateway between field devices and a safety PLC within a PROFINET/PROFIsafe environment.

\subsection{Attack Surface} 
The attack surface consists of all externally reachable interfaces and functions that may provide an entry point for an attacker. The following attack surfaces were identified: 

\begin{itemize} 
	\item HTTP-based IoTCore web interface 
	\item REST-API IoTCore services
	\item Firmware update mechanism
	\item Ethernet communication interfaces 
	\item PROFINET communication services
	\item PROFIsafe communication services
	\item PROFINET DCP configuration services
	\item Rotary switch interface
	\item EEPROM and persistent configuration storage
	\item Debug and programming interfaces (JTAG)
	\item Power supply interface
\end{itemize} 
Particular attention is given to the firmware update process, IoTCore services, network communication interfaces, and persistent configuration storage because they provide direct access to critical assets.

\section{Development of the Functional Security Testing Methodology}
\label{sec:testing_methodology_development} 


Problem aktueller Methodiken: 
- klassischer Funktionale Ansatz (Black-Box-Ansatz): Prüft nur Soll-Verhalten, Keine Aussage über Angriffswiderstand --> Für Nachweisführung regulatorischer Anforderungen allein nicht ausreichend
- Security Verificaton nach IEC 62443: Abstrakt, liefert keine konkreten Testfälle --> bietet aber Grundlage für die Ableitung systematischer Testfälle
- Penetration Testing: Geringe Reproduzierbarkeit, Ergebnis abhängig vom Tester -->  Für die Maschinenverordnung liefern Penetration Tests starke Evidenz, ersetzen jedoch keine strukturierte Verifikationsmethodik.
- Fuzz Testing: Erfordert spezialisiertes Testsetup, schwierige Ergebnisanalyse --> geeignet für Prüfung robuster Kommunikation und Fehlerbehandlung nach IEC 62443
- Protocol Security Testing
- OWASP IoT Security Testing Guide: nicht speziell für OT entwickelt
- Risk-based Security Testing: Aufwendige Riskoanalyse notwendig

In the context of industrial gateways, which act as critical boundaries at the IT/OT interface, these 
devices are primarily evaluated under the stringent requirements for network components.


Funktionale Tests prüfen, ob das System tut, was es soll. Security Tests prüfen, ob das System auch das unterlässt, was es nicht tun darf.
