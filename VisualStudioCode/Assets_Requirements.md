# Mapping Notes

**RQ-001** — Assets A, F and H were selected because the requirement's core concern (a connecting device must not cause a hazardous situation) directly threatens the trusted safety function (A), the separation between the compromised external channel and the safety domain (F, per trust boundary TB1), and overall device functionality (H). Interfaces IF-01, IF-02 and IF-03 were selected because they are the only interfaces classified as "External" or "External logical safety channel" in the Interface Asset Matrix — i.e., the only points where "another device" or "remote device" actually connects. Internal buses (IF-04, IF-05, IF-12) and local physical interfaces (IF-06 through IF-11) were excluded because they do not represent a connection from another/remote device.

**RQ-002** — Assets D and F were chosen because the requirement is scoped to hardware paths that transmit data relevant to *access to safety-critical software*, which is precisely what SysCom, the Shared Flash path, and JTAG provide, and both ultimately protect the integrity of the safety software (D) across the domain boundary (F). These three interfaces were selected because their documented "Relevant data flows" explicitly include firmware, configuration, or debug access; IF-01/IF-02/IF-06/IF-07 were excluded because they carry process/parameterization or field data rather than paths for accessing safety-critical software itself.

**RQ-003** — Because this is a logging/evidence requirement, the interfaces were chosen based on where a *hardware* intervention event would originate: physical JTAG access, physical rotary-switch manipulation, and the Shared Flash hardware write path, all of which are documented TARA threat scenarios (TARA-014, TARA-019, TARA-020) explicitly involving physical/hardware tampering. Assets D, F and G were included because they represent what is put at risk by such interventions (safety software, domain separation, operating mode). SysCom was excluded because it is an internal electrical bus without a documented "hardware intervention" TARA scenario of its own (its data-integrity aspects are already covered under RQ-002/RQ-005).

**RQ-004** — D and B were selected as the assets whose identity/criticality must be established, since the requirement is about identification, not protection. IoTCore, SysCom and Shared Flash were selected because they are the documented sources/carriers of software and version identification data. Field I/O, power and status interfaces were excluded because they carry no identification data about software or safety-critical data sets.

**RQ-005** — This requirement narrows RQ-004's identified objects (software and data) into a protection requirement, so C (process data) was added alongside D and B to reflect that SysCom also carries safety-relevant process data subject to corruption (TARA-010). The same three interfaces as RQ-002 were retained since they are the internal paths transmitting the now-identified software/data; external interfaces were excluded because RQ-001/RQ-010 already address external-connection risks and the TARA does not attribute software/data corruption scenarios to IF-01/IF-02.

**RQ-006** — D and G were chosen because "software installed... necessary for safe operation" maps to the firmware/update-workflow object (D) and the operating-mode-relevant software noted in TARA-006. IoTCore and Shared Flash were retained from RQ-004 as the two concrete sources of installed-software identity; SysCom was excluded here because it only transports rather than stores/exposes the installed-software identity.

**RQ-007** — E and H were added because "available at all times" is fundamentally an availability/diagnostics property, and D remains because the requirement concerns identification information of software. IoTCore was selected as the networked access point, and LED status indication was added specifically because it is the only always-on, locally observable interface in the source material, matching "easily accessible form." All interfaces lacking an information-output function were excluded.

**RQ-008** — D, G and E were selected because software intervention (legitimate or illegitimate) affects software integrity (D), operating mode if triggered via update/service functions (G), and depends on the monitoring function for evidence collection (E). IoTCore, SysCom, Shared Flash and JTAG were selected because each is a documented path by which the installed software can be accessed, triggered for update, or physically manipulated (TARA-006, TARA-007, TARA-013, TARA-020). Field I/O and power interfaces were excluded as they cannot access or alter installed software.

**RQ-009** — B was added to the RQ-008 asset set because configuration (not just software) modification is now in scope, and PROFINET (IF-01) and rotary switches (IF-08) were added because they are the two additional documented configuration-modification vectors (TARA-001, TARA-019) not relevant to RQ-008's software-only scope. Process-data-only or observation-only interfaces (IF-02, IF-06, IF-07, IF-11, IF-12) were excluded because the Interface Asset Matrix and TARA do not attribute any configuration- or software-modification capability to them.

**RQ-010** — H, F and A were selected because resilience against malicious third parties is fundamentally an availability requirement (H) with a hazardous-situation consequence if the safety domain is affected (F, A). The four interfaces were selected strictly because each has an explicit Denial-of-Service or external-reachability TARA scenario (TARA-002, TARA-004, TARA-008, TARA-021, TARA-024); no other interface has a documented DoS/resilience scenario. Local/internal-only interfaces were excluded because the SUC assumption explicitly states deployment is fieldbus/cell-level with no direct internet exposure, making them not reachable by "third parties" in the assessed environment.

**RQ-011** — B and A were selected because the requirement is a direct configuration-integrity protection requirement affecting safety-relevant settings and, through them, the safety function. PROFINET, SysCom and rotary switches were selected as the three documented configuration-change mechanisms (TARA-001, TARA-009, TARA-019). The "learning phase" clause could not be mapped to any asset or interface because no adaptive/learning configuration mechanism is described anywhere in the provided TARA or asset documentation — this is noted as an explicit traceability gap rather than an assumed mapping.

**RQ-012** — E, D and G were selected because intervention-related tracing-log data originates from the monitoring/diagnostics function and concerns software and operating-mode events. IoTCore and Shared Flash were selected as, respectively, the documented log-retrieval endpoint and the only persistent storage medium described in the source material. The five-year retention duration is not itself verifiable against any interface in the provided documents, since no retention/storage-lifecycle mechanism is described — this limitation is noted rather than assumed.

**RQ-013** — D was selected as the sole asset because the requirement is narrowly about safety-software version data. IoTCore (firmware update handling) and Shared Flash (version information) were retained as the two documented locations where upload/version events are recorded. As with RQ-012, the five-year-per-upload retention period has no corresponding verification point in the source documents beyond the data-origin interfaces.

**RQ-014** — E and G were selected because the requirement concerns restricting access to log data (an E-asset artifact) under an authorization/operating-mode gate (G). IoTCore was selected as the only interface in the source material through which diagnostic/log data is exposed and through which authorization-gated service functions are invoked (TARA-005, TARA-007). No other interface has a documented log-access capability, so the mapping is intentionally narrow per rule 4 (avoid overly broad mappings).
