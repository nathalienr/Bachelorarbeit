3 System Context
The "Safe Remote IO" [SRIO] is a functional safety gateway which transfers safe input signals to a upper Host, or switches
functional safety actuators based on process data signals received from the upper Host. The input and output ports are
compatible to certain ZVEI types (Interface definition of the Safety Inputs/Outputs). An IoT-Connection via HTTP / JSON is only
for none-safety related functionalities e.g. supervision of voltage/current values or firmware update of the SRIO.

3.3 External Interfaces
3.3.1 Fieldbus
The Safe Remote IO will be used in a fieldbus system with an existing plc (F-Host). As displayed (solid lines) the PROFINET
connection is handled by the COM Module while the safety related communication protocol (PROFIsafe) is handled by the SCPU
Module. With dottet lines the direct dependencies are marked which are relevant for e.g. Watchdogtimings since there are 2
different, the one for PROFINET and the F_WD_Time for PROFIsafe.

The usage of the black channel (tunneling the PROFIsafe Frame through a none-safety-related communication) enables the
system to keep the COM Module also none-safety-related. PROFINET Diagnosis is handled by COM, which means the SCPU will
inform COM via SysCom for each error detected which will than mapped to a PROFINET Diagnosis by COM.

3.3.2 IoT-Core
The IoT Core provides an interface to the functionality and data of a device. This interface is being accessed via the fieldbus
ports and handled in parallel to the fieldbus communication. For the IoT Core a device is composed of:

      DATA - Data can be provided in many different formats and many different ways to access it.
      SERVICES - Services can be invoked from outside the IoT Core and will deliver a response
      EVENTS - Events send out notifications to subscribers when they are triggered
      STRUCTURE - to organize DATA, SERVICES and EVENTS

3.3.3 Rotary Switch Interface
The Rotary Switch have a multi function purpose with each switch having a different multiplication factor to achieve a number
range between 0 and 999 decimal.

 STATE NAME                    STATE DESCRIPTION

 Off                           In this state the System is not powered. With "power on" the system transition to Init.
                               All States are able to transition to Off, for visibility reasons not all those transitions are included in the
                               state diagram.

 Init                          When entered, the system (COM and SCPU) initializes itself. During state Init the self tests are
                               executed and all internal communications are set up and running when this state is left. The system
                               reached the ability to detect errors. Flowchart of internal transitions 5.1 - State Init

 Parametrization               When entered, the system initiates the external fieldbus communication. Via the established
                               connection, the received configuration (consist of F_Par and iPar) are verified and applied if correct.
                               The safe communication protocol is initiated and established.
                               Flowchart of internal transitions 5.2 - State Parametrization

 Operate                       When entered the system had received the integration request to start the safe communication with
                               the external F_Host. The system is running and cyclic process data is exchanged.
                               Flowchart of internal transitions 5.3 - State Operate

 Update                        This state handles the firmware update of the system. See 5.4 - State Update

 FatalError                    This state handles any error which caused the system to lose the ability of a safe functionality.
                               See 5.5 - State Fatal Error.

The classification of an error into one of the error classes shall be done when describing the respective error.            ,    SIL 3

   SRIO-9917 - Error Class 1 - FATAL ERROR
   Error class 1 describes errors that compromise the overall integrity of the system.


   Remark:
   Those are errors in the central components of SRIO, which impacts the behavior of other components/functions which no longer
   can be operated correctly.
   (Causes could be e.g. Error detected by Selftestlibrary or PROFIsafe Stack request Fatal Error)                          ,    SIL 3

       SRIO-10705 - Error Class 1 - Reset
       Error of categories 1 shall require a coldstart.                                                                     ,    SIL 3

   SRIO-10702 - ErrorCategory 3: COMMUNICATION ERROR
   Error class 3 describes errors related to the external communication.


   Remark:
   Those are errors which impacts the communication to the plc due to which the operational functionality can no longer be
   carried out correctly.
   (Causes could be e.g. Invalid configuration recieved or loss of communication)                                           ,    SIL 3

       SRIO-10816 - Error Category 3: Reset
       Error of category 3 require a transition to state Parametrization and a communication restart.                       ,    SIL 3

   SRIO-10701 - ErrorCategory 4: CHANNEL/PORT ERROR
   Error class 4 describes Errors that prevent a function from being performed correctly.


   Remark:
   Those are errors in functionalities of SRIO which do not impact the overall integrity. The User is able to acknowledge the error to
   regain operational functionality.
   (Causes could be e.g. Failed Testpulse of an IO)                                                                         ,    SIL 3

       SRIO-10815 - Error Category 4: Reset
       Error of Category 4 require an acknowledge by the user.                                                              ,    SIL 3

       SRIO-10639 - Errorhandling Port
       In case of an error on one channel, both channels of the port shall be handled together.                             ,    SIL 3

   SRIO-21648 - Error Category 5: Failsafe Fieldbus Communication Error
   Error class 5 describes Errors which are detected by the communication stack of the failsafe fieldbus communication.


   Remark:
   Those are errors like F_WD_Timeout or CRC mismatch.                                                                      ,    SIL 3

8.4.1 ZVEI
ZVEI categorizes Digital Inputs in 3 Types: A, B , C.
Type A is generally used for passive sensordevices which do not provide a measure to validate errors on the signalline, therefore
the sink of the sensor signal will provide a testpulse to detect any crosscircuit.
Type B this Type is not implemented in SRIO.
Type C has in contrast to type A sensor devices which provide their own testpulse. For those devices SRIO shall not use a
testpulse and has to filter the sensor testpulse.

9.1 Sequence Diagram of Update
The DIL Switches has to be set to 999 [#1] and a power cycle has to be performed by the user to enable the system to switch to
the Update state. During booting CPU1 reads the DIL setting and switches to Update [#3].
CPU1 requests during initialization the DIL-State [#4] and will be informed by CPU1 [#5]. CPU2 will continue with a normal boot
[#6] and is reset by CPU1 [#7]. Reset Cause is detected by CPU2 [#8] which causes also a boot to update state.


The User will upload the Update Container to SRIO [#11], which will be saved to the Flash of COM Module. After reception of
the Update Container CPU3 will start with the Update [#12] by updating the Netx90 and resetting itself to start the bootloader.
After the Update of COM is done, CPU3 will move the Update Container to the shared Flash [#13] and inform CPU1 to begin
updating the SCPU Module [#14]. While CPU1 is validating the Update Container [#15] and performing the Update [#16] the
safe state is ensured by Watchdog aswell as CPU2.
After CPU1 is done updating itself, the internal startup tests are performed [#17] to ensure a functional firmware. If successful
CPU3 is informed [#18] and the update continued by resetting [#19], flashing [#20] and restarting [#21] CPU2. During the
Update of CPU2 the safe state is ensured by Watchdog and CPU1. CPU2 boots and performes also the internal startup test [#22]
CPU1 signals to CPU3 a succesful update [#23] and performs a softreset [#24].
Triggered by the successfull update command by SCPU, COM starts the IoTCore [#25].
This enables the User to verify the installed firmware versions [#26].

11.4 ifm-CRC-Tool
The tool is used to verify the device parameters, i.e., to check whether the parameters are correct for the application. With
PROFIsafe, this involves setting the PROFIsafe individual parameters. Regardless of this, the user must check whether the
required safety functions work as expected (validation of safety functions). This is not within the scope of the tool or this
document. The devices are IO modules with safe digital inputs and outputs. The first devices supported are “AL400S” and
“AL401S,” each with 8 safe IO ports. The individual parameters are used to parameterize the properties of these IO ports.
SRIO-20273 - ifm-CRC-Tool --- Instruction regarding setting and verification of individual parameters
The SRIO user manual shall contain instructions regarding the procedure of setting and validation the individual parameter
using the ifm-CRC-Tool.


Remark:     SRIO-20272 contains the original text from the supplier.                                                       ,    SIL 3

   Original Text from Chapter 2.1 Einstellung und Verifikation der Individual-Parameter
   Die PROFIsafe-Individual-Parameter sind bei den unterstützen Devices „AL400S“ und „AL401S“ Teil der Projektierung (GSD) des
   verwendeten Steuerungssystems (SPS-Tool), z.B. TIA Portal von Siemens. Die PROFIsafe-Individual-Parameter (iParameter) sind
   in der PROFINET Gerätebeschreibung GSD für diese Geräte beschrieben. In der Hardware-Konfiguration des SPS-Tools werden
   die iParameter angezeigt und können dort eingestellt werden. Bei jedem Anlauf des Steuerungssystems werden diese Parameter
   von der SPS auf die IO-Module übertragen. Zur Absicherung der Parameter gegen unbeabsichtigte Veränderung bei der Eingabe
   und bei der Übertragung gibt es den iPar-CRC. Da es sich bei dem SPS-Tool um keine sichere Implementierung handelt, muss
   der Anwender die korrekte Einstellung der iParameter mit dem „ifm-CRC-Tool“ verifizieren. Dazu werden die iParameter über
   das Tool Calling Interface (TCI) vom SPS-Tool an das „ifm-CRC-Tool“ übertragen. Dort werden sie mit einer vom SPS-Tool
   diversitären Implementierung angezeigt. Der Anwender muss die Anzeige im SPS-Tool und dem „ifm-CRC-Tool“ für jeden
   Parameter vergleichen und dann die Korrektheit der Einstellungen bestätigen. Wenn die Liste der iParameter länger ist als in
   einer Bildschirmseite angezeigt werden kann, muss der Anwender die Parameterliste beim Vergleich nach unten scrollen. Nur
   wenn alle iParameter sichtbar waren, kann er seine Überprüfung als korrekt bestätigen. Das „ifm-CRC-Tool“ berechnet dann
   den iPar-CRC über die verifizierten iParameter und zeigt diesen wahlweise in hexadezimaler oder dezimaler Darstellung an. Der
   Anwender kann den iPar-CRC dann durch einen Button in die Zwischenablage übernehmen oder ihn manuell in diese
   übernehmen. Aus der Zwischenablage kann er den iPar-CRC dann im SPS-Tool einfügen. Das SPS-Tool trägt die iParameter und
   den iPar-CRC in die Konfiguration der SPS ein. Diese überträgt bei jedem Anlauf die iParameter und den iPar-CRC an das
   Device. Die Device-Firmware prüft dann die beim Anlauf von der SPS übertragenen iParameter und den iPar-CRC.
